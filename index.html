IDiagnóstico AS-IS Responsable: Diego

Un flujo sin contrato ni estado

Situación actual

InventoryService publica un evento delta en JSON plano y sin esquema cada vez que cambia el stock:

{ "productId": "X123",
  "stockChange": -2 }

Consecuencia

PurchasingService necesita saber si debe reabastecer, pero el delta no le dice el total. Para averiguarlo consulta la base de datos de Inventarios, y eso satura sus APIs.

Falla 01

Ruptura silenciosa del esquema

Inventarios renombra stockChange a delta sin aviso. Sin Schema Registry no hay gatekeeper en la ruta de escritura.

Falla 02

Consulta síncrona de retorno

El delta no lleva estado. Reaparecen el acoplamiento punto a punto y la disponibilidad invertida.

Falla 03

Historial no compactable

Cada delta es necesario para reconstruir el total. Un consumidor nuevo debe procesar toda la historia.

IIIDiseño del evento ECST · Estructura Responsable: Daniel

El evento transporta el estado, no la variación

{ "productId": "X123", "stockChange": -2 }
  • Describe qué pasó, no cuánto hay.
  • Si el evento llega dos veces, el descuento se aplica dos veces.
  • Para conocer el total, el consumidor debe llamar a Inventarios.
// Kafka · tópico inventory.stock.state.v1
// key = "X123"
{
  "eventId":      "6f1c2a9e-4b7d-4e2a-9c31-8d5f0e7b2a14",
  "eventType":    "InventoryStockStateUpdated",
  "productId":    "X123",
  "currentStock": 48,
  "version":      17,
  "occurredAt":   "2026-10-25T14:32:05.120Z"
}
CampoRol
eventIdIdentidad del mensaje; permite descartar duplicados.
eventTypeClasifica el evento: actualización o snapshot de reconciliación.
productIdClave de negocio y de partición.
currentStockEstado actual completo: el dato que hoy obliga a consultar la API.
versionContador creciente por producto; ordena y evita sobrescribir con un estado viejo.
occurredAtMomento en que el estado fue válido.
IIIDiseño del evento ECST · Justificación Responsable: Daniel

Por qué reduce la carga de la API síncrona

Cero consultas de retorno

PurchasingService lee currentStock del propio evento. La API síncrona de Inventarios sale del camino crítico del reabastecimiento.

Autonomía del consumidor

Si InventoryService cae, Purchasing sigue decidiendo con su proyección local. La disponibilidad deja de estar invertida.

Desacoplamiento

El contenido del evento lo define el bounded context de Inventarios. Purchasing nunca conoce su base de datos ni su modelo interno.

Idempotencia y orden

Reprocesar un estado da el mismo resultado. Con version, el consumidor ignora todo evento cuya versión no supere la que ya tiene.

Regla de materialización en PurchasingService

al recibir evento e:
  actual = proyeccion.get(e.productId)
  si actual == null  o  e.version > actual.version:
      proyeccion.upsert(e.productId, e)      // estado más reciente
      si e.currentStock <= puntoDeReorden(e.productId):
          generarOrdenDeCompra(e.productId)
  si no:
      descartar(e)                            // duplicado o desordenado

El punto de reorden pertenece al dominio de Compras, por eso no viaja en el evento de Inventarios.

IVData Contract · JSON Schema Responsable: Andrés

Contrato formal del State Event

{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "$id": "https://retailcore.example/schemas/inventory/stock-state/v1.json",
  "title": "InventoryStockState",
  "description": "Estado actual del inventario de un producto (ECST). Dueño: equipo de Inventarios.",
  "type": "object",
  "properties": {
    "eventId":      { "type": "string", "format": "uuid",
                      "description": "Identificador único del evento." },
    "eventType":    { "type": "string",
                      "enum": ["InventoryStockStateUpdated", "InventoryStockSnapshot"],
                      "description": "Actualización de estado o snapshot de reconciliación." },
    "productId":    { "type": "string", "minLength": 1, "maxLength": 64,
                      "pattern": "^[A-Z0-9-]+$",
                      "description": "Identificador del producto; clave de partición." },
    "currentStock": { "type": "integer", "minimum": 0,
                      "description": "Unidades disponibles al momento del evento." },
    "version":      { "type": "integer", "minimum": 1,
                      "description": "Versión creciente del estado del producto." },
    "occurredAt":   { "type": "string", "format": "date-time",
                      "description": "Fecha y hora ISO-8601 en UTC." },
    "reservedStock": { "type": "integer", "minimum": 0,
                      "description": "Opcional. Unidades comprometidas en pedidos." },
    "warehouseId":  { "type": ["string", "null"],
                      "description": "Opcional. Bodega de origen." }
  },
  "required": ["eventId", "eventType", "productId",
               "currentStock", "version", "occurredAt"],
  "additionalProperties": true
}
IVData Contract · Obligatorios y validaciones Responsable: Andrés

Qué es obligatorio y qué se valida

CampoTipoEstadoValidación
eventIdstring · uuidrequiredFormato UUID
eventTypestring · enumrequiredSolo los valores del catálogo
productIdstringrequired1–64 caracteres, mayúsculas, dígitos y guion
currentStockintegerrequiredEntero ≥ 0, sin decimales
versionintegerrequiredEntero ≥ 1
occurredAtstring · date-timerequiredISO-8601 (RFC 3339)
reservedStockintegeropcionalEntero ≥ 0 cuando viene
warehouseIdstring | nullopcionalAdmite null explícito

Cómo se expresa la obligatoriedad en JSON Schema

Un campo es obligatorio si aparece en required; los demás son opcionales. El tipo de cada campo es explícito: no hay object libres ni tipos genéricos. Los dos opcionales son propuesta para discutir en el equipo; la línea base aprobada son los seis obligatorios.

A verificar en la implementación

Las palabras clave format (uuid, date-time) no siempre se validan por defecto: depende del validador. Hay que confirmar que el serializador las aplica o reforzarlas con pattern.

VPolítica de compatibilidad · Decisión y limitaciones Responsable: Maycol

FULL_TRANSITIVE: qué protege y qué cuesta

Protege

Los campos críticos

Eliminar un campo obligatorio, volverlo opcional o renombrarlo (que equivale a eliminar uno y añadir otro) rompe la lectura de los consumidores viejos. FULL_TRANSITIVE lo rechaza contra cualquier versión histórica.

Limitación

La evolución en JSON Schema

En JSON Schema la compatibilidad depende del modelo de contenido. Con modelo abierto (additionalProperties: true) o cerrado, añadir o quitar propiedades opcionales tampoco pasa una verificación FULL.

No protege

La semántica

Si currentStock pasa a significar «stock más reservas», el esquema no cambia y el Registry no lo detecta. Eso se cubre con revisión del contrato por los consumidores.

Decisión propuesta

Configurar FULL_TRANSITIVE en el subject inventory.stock.state.v1-value, porque el tópico es compactado y un consumidor nuevo lo relee desde el offset 0. Para poder añadir campos opcionales en el futuro sin romper la política, el equipo debe elegir entre un modelo de contenido parcialmente abierto o publicar una versión mayor en un tópico v2 con producción dual.

VIEscenario · Mecanismos de prevención Responsable: Rubén

Cuatro barreras antes de producción

1 · Pull request

Revisión del contrato

El esquema vive en el repositorio y cada cambio pasa por un PR que aprueban los dueños de los consumidores.

2 · CI

Prueba de compatibilidad

El pipeline consulta la API de compatibilidad del Registry antes de construir. Un esquema incompatible detiene el pipeline.

3 · Registro

Sin autorregistro

En producción, auto.register.schemas=false: el productor solo usa esquemas ya registrados por el pipeline.

4 · Serializador

Validación del payload

Si el código omite productId aunque el esquema no cambie, el serializador valida contra el esquema y rechaza el mensaje.

Si el cambio es realmente necesario

Un cambio destructivo legítimo no se fuerza sobre v1: se publica inventory.stock.state.v2, se produce en ambos tópicos durante una ventana de migración acordada y se marca v1 como obsoleto.

VIIConclusiones y referencias

Conclusiones

  • El evento de estado reemplaza la llamada síncrona de retorno por una proyección que PurchasingService mantiene por sí mismo.
  • version y la clave productId dan orden e idempotencia por producto.
  • El contrato en JSON Schema hace explícitos los tipos, los obligatorios y las validaciones.
  • FULL_TRANSITIVE protege los campos críticos, pero en JSON Schema exige decidir el modelo de contenido para poder evolucionar.
  • Un cambio destructivo se detiene en la ruta de escritura, no en producción.
